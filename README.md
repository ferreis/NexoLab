# NexoDB Lab

Modelador visual de propostas de banco de dados PostgreSQL/Supabase, feito com **Vue 3**, **Pinia** e **Vite**.

## Executar localmente

Requer Node.js 20.19+ (ou Node 22.12+ / 24+).

```bash
git clone https://github.com/ferreis/NexoLab.git NexoLab
cd NexoLab
git checkout Dev
npm install
npm run dev
```

Abra o endereço mostrado pelo Vite (normalmente `http://localhost:5173`).

O campo **Comentário**, abaixo do nome da tabela, aceita explicações em várias linhas. O JSON preserva o texto em `comentario` e inclui o comando correspondente em `comentario_sql` quando preenchido. O TXT mostra `COMMENT ON TABLE "schema"."tabela" IS 'texto';` abaixo do título da tabela. Aspas e barras são escapadas no SQL; alterações no nome da tabela ou no schema atualizam o comando automaticamente. Importação e armazenamento local preservam o texto para edição, e modelos antigos abrem com o campo vazio.

Cada coluna também possui um campo **Comentário**, separado de **Regra**. O JSON da coluna guarda `comentario` e o comando gerado em `comentario_sql`; o TXT apresenta `COMMENT ON COLUMN "schema"."tabela"."coluna" IS 'texto';` logo após a linha da coluna. O comentário acompanha renomeações de schema, tabela e coluna, com a mesma preservação de texto e escape usados nos comentários de tabela.


A opção **Prévia**, no seletor do menu lateral esquerdo, abre uma página central dedicada a TXT/JSON. A opção **Tabela** mostra somente a tabela selecionada, suas colunas e seus relacionamentos e CHECKs; objetos globais do schema (ENUMs, funções e comentários gerais) aparecem apenas em **Esquema completo**.

## Diagramas Mermaid: mapa de ligações e diagrama ER

No seletor do menu lateral, escolha **Diagramas**. O visualizador usa o modelo local para gerar duas representações gráficas e uma visualização de código Mermaid, atualizadas automaticamente conforme as tabelas são editadas:

- **Ligações**: mapa de dependências das FKs (setas da tabela que contém a FK para a tabela referenciada), incluindo tabelas sem relações e aviso para referências externas ausentes.
- **Banco ER**: entidades com suas colunas, tipos, PK, FK, UNIQUE individual, indicação de NULL/NOT NULL e relacionamentos com cardinalidade aproximada a partir das FKs. CHECKs, UNIQUEs compostos e triggers permanecem documentados no editor e no JSON, pois não cabem integralmente na notação ER.
- **Código**: substitui o mapa pelo código Mermaid gerado para o último tipo gráfico selecionado (Ligações ou Banco ER). Ao voltar ao mapa, a seleção é preservada.

Escolha **Todas as tabelas** ou **Tabela e ligações** para destacar a tabela selecionada e suas vizinhas. As opções **Visualização**, **Direção** e **Tema** ficam na barra superior do diagrama. É possível ampliar com a roda do mouse, arrastar o canvas e ajustar à tela. Os botões **Copiar Mermaid**, **Baixar .mmd**, **SVG** e **PNG** ficam no rodapé do próprio diagrama. A aba **Código** exibe o Mermaid em toda a área de visualização, com rolagem interna, substituindo a antiga seção de código separada.

A renderização usa a dependência Mermaid instalada localmente e o nível de segurança `strict`. O SVG é exibido como imagem em vez de HTML ativo. Nenhum esquema é enviado a um serviço externo, e o visualizador não modifica o banco nem executa SQL.

## Edição em massa e refatoração de FKs

O botão **Edição em massa** fica no cabeçalho do modelador. Pesquise por tabela ou nome de coluna, marque os resultados individualmente ou use **Selecionar resultados**, e escolha uma alteração: **substituir trecho no nome**, **alterar tipo de dado**, **Permite NULL**, **Imutável** ou **Valor padrão**. A renomeação mostra o valor anterior e o novo nome antes da confirmação. Operações que gerariam nomes duplicados são recusadas sem alterar o documento.

Quando uma **tabela é renomeada**, o modelador atualiza automaticamente as FKs que apontam para ela. Caso uma coluna de FK siga o nome exato da tabela antiga ou sua forma singular seguida de _id, ela também é renomeada. Exemplo: renomear **cenas_acoes** para **acoes** transforma uma FK **cena_acao_id** em **acao_id**, atualizando sua referência e os CHECKs e constraints associados. Nomes não padronizados são preservados. Para outras mudanças em lote, use a substituição de trechos da edição em massa.

**+ ID e datas padrão** aplica os três presets à tabela selecionada, criando colunas ausentes ou atualizando as existentes para os valores esperados. O botão **Padrões em todas as tabelas** faz o mesmo em todo o projeto após confirmação. Os padrões são:
- id: BIGINT, PRIMARY KEY, UNIQUE, NOT NULL, GENERATED BY DEFAULT AS IDENTITY, imutável, regra "Identificador único automático."
- criado_em: TIMESTAMPTZ, NOT NULL, DEFAULT now(), imutável, regra "Preenchido na criação do registro. Imutável após o primeiro preenchimento."
- atualizado_em: TIMESTAMPTZ, NOT NULL, DEFAULT now(), editável, regra "Preenchido na criação e atualizado automaticamente a cada alteração do registro."

Caso uma tabela já possua PK em outra coluna, a opção global respeita essa chave e ignora a padronização de id nessa tabela. As datas continuam sendo padronizadas. Nenhuma operação modifica as linhas de um banco real.

Os CHECKs de CREATE TABLE e ALTER TABLE são importados diretamente no editor de CHECKs. Ao editar/remover um CHECK originado de uma constraint SQL, sua definição SQL correspondente é atualizada/removida, evitando divergência entre o formulário e os metadados salvos.

## Importar definições SQL

Clique em **Importar SQL**, cole uma definição PostgreSQL ou escolha um arquivo .sql/.txt de até 4 MB, e depois em **Analisar SQL**. Uma prévia informa as quantidades de tabelas, colunas, restrições, triggers, tipos ENUM, funções e políticas RLS. Por fim, escolha uma das opções:

- **Mesclar com o projeto:** adiciona tabelas e colunas ainda não presentes. Tabelas e colunas com o mesmo nome são preservadas, inclusive alterações feitas manualmente. Restrições SQL, índices, triggers, políticas, enums e funções são incorporados sem duplicar declarações idênticas. O mesmo arquivo pode ser importado novamente sem gerar tabelas ou colunas duplicadas.
- **Substituir modelo atual:** limpa as tabelas e definições do modelo local e importa somente as do SQL. Exige confirmação adicional no diálogo. Não executa DROP TABLE nem qualquer outra instrução no banco real.

O parser aceita CREATE TABLE, CREATE TYPE ... AS ENUM, CREATE [OR REPLACE] FUNCTION, CREATE TRIGGER, índices, CREATE POLICY, ALTER TABLE ... ADD CONSTRAINT, ALTER COLUMN ... ADD GENERATED ... AS IDENTITY, comentários de tabela/coluna/tipo/função/schema e controles RLS. Reconhece SQL do painel Supabase e exportações de schema feitas por pg_dump. Restrições SQL complexas e políticas RLS permanecem em **Definições SQL importadas** na tabela; enums e funções podem ser consultados na barra lateral.

Tipos não representados no seletor visual são registrados como **CUSTOM**, mantendo seu tipo PostgreSQL original. O leitor não é um executor SQL nem substitui uma ferramenta de migração: estruturas não suportadas precisam de revisão manual. O JSON exportado preserva os metadados SQL reconhecidos e permite restaurá-los posteriormente. O TXT continua sendo um relatório de modelagem, não um script SQL executável.

## Funcionalidades

- Editor de tabelas e colunas; inserção de ID e datas padrão sem duplicação.
- Botão **Duplicar coluna** ao lado de **Excluir coluna** em cada cartão: cria uma cópia com nome exclusivo (`nome_copia`, `nome_copia_2`), aberta para edição, preservando tipo, tamanho, regras, comentários, FKs e CHECKs. A cópia tem novo identificador e novos IDs de CHECK; PK, identidade automática, vínculos de UNIQUE composto e nomes de constraints SQL importadas não são replicados para evitar conflitos.
- Valor padrão na criação, opção de coluna imutável e regras em texto livre, incluídos nas propostas TXT/JSON.
- Suporte a ENUM, VARCHAR, NUMERIC, tipos comuns do PostgreSQL, PK, FK, NULL e UNIQUE.
- Ajuda contextual para os tipos de dados.
- Menu lateral esquerdo recolhível com seletor personalizado e navegação por Tabelas, Enum, Triggers, Functions e Prévia.
- Prévia TXT/JSON em tela central, com alternância entre esquema completo e tabela selecionada, cópia fiel e rolagem própria.
- Diagramas Mermaid de ligações FK e banco ER, com canvas navegável, escopo por tabela e exportação de código, SVG e PNG.
- Reordenação das colunas pela alça de arrastar ou pelas setas do teclado, mantendo ID e datas fixos; ordem preservada ao salvar e exportar.
- Exportação TXT/JSON e importação do JSON da ferramenta HTML anterior.
- Persistência automática local via `localStorage`.
- Regras de negócio, validações e triggers no campo Regra de cada coluna.
- UNIQUE composto configurado dentro das colunas, com seleção das demais colunas da combinação e exportação em TXT/JSON.
- CHECK com múltiplas expressões SQL por coluna, incluindo condições que envolvem várias colunas da mesma linha, edição e exportação em TXT/JSON.

**Não se conecta ao Supabase e não executa SQL.** O JSON é uma proposta para revisão.

Os presets são exibidos fechados: `id` sempre no início, `criado_em` e `atualizado_em` no fim. Novas colunas entram no meio. Nos presets, `id` e `criado_em` são imutáveis após o primeiro preenchimento; as datas recebem `now()` na criação. A atualização de `atualizado_em` fica descrita nas regras da coluna. Essas regras integram a proposta, a implementar no banco ou na aplicação. Ao abrir ou importar modelos antigos, automações da tabela são incorporadas às regras e a antiga opção de atualização de datas é preservada como texto nas observações da coluna.

Ao marcar PK, o modelador exige imutabilidade e NOT NULL. Uma PK de uma coluna também marca UNIQUE automaticamente. Se várias colunas forem marcadas como PK, elas formam uma única chave composta: a unicidade vale para a combinação, e UNIQUE individual continua opcional. Desmarcar PK mantém as opções explícitas de imutabilidade e nulidade para revisão. FK, por si só, permite valores repetidos. A imutabilidade é uma regra desta ferramenta, não uma restrição implícita de PK no PostgreSQL.

Para números de parcelas únicos por financeiro, abra uma das colunas, marque **UNIQUE**, depois **Composto** e clique em **Adicionar unique compose**. Selecione a outra coluna e adicione a combinação `(financeiro_id, numero)`. Assim, `(1, 6)` e `(2, 6)` são permitidos, mas duas ocorrências de `(1, 6)` são rejeitadas quando a restrição for implementada no banco. O modo composto desativa o UNIQUE individual. Desmarcá-lo remove as combinações da coluna e volta ao UNIQUE individual; desmarcar UNIQUE remove também suas combinações. As colunas não precisam ser FKs para participar.

Depois de definir uma PK, a opção PK fica oculta nas outras colunas. A coluna que já é PK mantém o controle para permitir desmarcá-la e escolher outra. O botão de ID e datas padrão preserva a PK existente e não adiciona outra. Modelos antigos com PK composta continuam sendo importados.

O JSON inclui `uniqueCompostos: [{ "colunas": ["financeiro_id", "numero"] }]` em cada tabela; o TXT descreve a mesma combinação. Os grupos acompanham renomeações e reordenações, são restaurados ao importar e aparecem nas colunas participantes. Excluir uma coluna remove as combinações inteiras que dependiam dela. Se Permite NULL estiver marcado, vale o comportamento padrão do PostgreSQL: combinações contendo NULL podem se repetir. A ferramenta registra a proposta, sem executar a restrição no banco.

Novos CHECKs abrem no modo **SQL**, para colar ou escrever uma expressão. A ação **Adicionar restrição** fica na mesma barra dos botões **SQL** e **Montar**. Use **Converter para seleções** para abrir o formulário **Montar** com os grupos preenchidos; com SQL vazio, também é possível escolher **Montar** para começar pelas seleções. No formulário, escolha a coluna, a condição e um valor ou outra coluna para comparar. Cada grupo tem seu próprio operador **E/OU** e pode receber condições ou **subgrupos recursivos**, sem o limite anterior de dois níveis. Parênteses preservam o agrupamento ao gerar SQL. Valores booleanos e de ENUM usam listas de seleção. Números personalizados e textos podem ser informados no campo de valor. Os botões **+ UNIQUE Compose** e **+ CHECK** ficam juntos abaixo das opções da coluna. Os conteúdos de CHECK e UNIQUE Compose podem ser expandidos ou recolhidos sem esconder esses botões; salvar uma restrição recolhe a seção. Recolher durante a edição preserva as seleções ainda não salvas. É possível adicionar, editar e excluir várias restrições na mesma coluna ou tabela. O PostgreSQL rejeita o registro quando uma condição CHECK é FALSE; TRUE e NULL satisfazem a condição, portanto CHECK não substitui NOT NULL e não é uma trigger.

Os CHECKs ficam no JSON de cada coluna como `checks: [{ "expressao": "numero >= 1" }]`. Regras criadas por seleções também guardam `construtor`, com grupos, condições e valores, para reabrir a edição visual após importar ou recarregar. Novos grupos usam `{ operador, itens }`; cada item pode ser uma condição ou outro grupo. Os formatos antigos com `grupos` e `condicoes` continuam importando. O SQL é gerado com identificadores e valores escapados; os CHECKs do construtor acompanham renomeações e são removidos quando uma coluna da qual dependem é excluída.

No modo **SQL**, cole uma expressão ou `CHECK (...)` e clique em **Converter para seleções**. A conversão suporta parênteses, AND/OR, comparações (`=`, `<>`, `!=`, `>`, `>=`, `<`, `<=`), números, textos entre aspas simples, TRUE/FALSE, comparação entre colunas e IS NULL/IS NOT NULL, respeitando a precedência de AND sobre OR. Identificadores entre aspas duplas preservam a caixa; nomes sem aspas são convertidos para minúsculas como no PostgreSQL. Funções, casts, subconsultas e outros recursos fora desse subconjunto permanecem no modo SQL, com mensagem explicativa e o texto original preservado. A conversão não executa SQL. Expressões que permanecerem livres continuam exigindo revisão manual ao renomear ou excluir colunas.

O TXT documenta UNIQUE individual e UNIQUE Compose apenas na linha da coluna de origem, e os CHECKs na mesma linha da coluna em que foram cadastrados, separados por `|`. Não há linha vazia entre o título da tabela e suas colunas; tabelas consecutivas são separadas por uma linha vazia. O TXT compacta os CHECKs e remove parênteses externos redundantes; o JSON preserva as expressões originais e os dados estruturados para edição e importação. Prévia, cópia e download usam essa mesma formatação, com cláusulas `CHECK (expressão)` do formatador PostgreSQL compartilhado. A primeira coluna de cada composição identifica a origem do cadastro no JSON e no armazenamento local; a ordem é preservada ao importar e reordenar colunas. As demais colunas participam da restrição, sem repetir o cadastro ou a indicação na interface e no TXT. Uma tabela pode ter várias composições, inclusive criadas na mesma coluna. O modelo atual oferece TXT/JSON, sem exportador SQL completo nem execução ou validação de sintaxe contra um banco. Desmarcar CHECK remove as restrições cadastradas naquela coluna. Modelos antigos sem o campo `checks` continuam sendo importados.

## Navegação por objetos do schema

A barra lateral mantém o campo **Schema** e oferece um seletor estilizado no título para alternar entre **Tabelas**, **Enum**, **Triggers**, **Functions** e **Prévia**. O menu suporta teclado (setas, Home, End, Enter e Escape), clique externo para fechar e destaca a categoria ativa. Os contadores mostram objetos existentes no projeto: tabelas, enums, triggers registradas nas tabelas e funções SQL globais. A lista é ordenada alfabeticamente.

Clicar numa tabela seleciona o editor visual. Clicar num ENUM abre seus valores e sua definição SQL para consulta e cópia. Clicar numa trigger abre a definição e sua tabela vinculada, com atalho para selecionar a tabela. Clicar numa função abre o editor de funções SQL existente. O botão **+** cria uma tabela ou inicia uma nova função quando a categoria correspondente está ativa. Nenhuma dessas ações executa SQL no PostgreSQL. O nome do projeto continua preservado no JSON existente, mas seu campo foi removido da barra lateral.

## Edição das regras do schema e prévia completa

Na barra lateral, o campo **Schema** tem um botão compacto **Regras**. Ele abre um diálogo para editar o texto das regras do schema, mantendo o autocomplete de funções por `#` e atalhos para navegar até suas definições. O texto é salvo ao clicar em **Salvar regras**; fechar ou cancelar descarta alterações pendentes.

Escolha **Prévia** no seletor lateral para abrir o visualizador na área central, sem painel direito. Use **Esquema completo** ou **Tabela**, escolha **TXT** ou **JSON** e clique em **Copiar** para obter exatamente o texto exibido. O menu esquerdo permite escolher uma tabela sem sair da prévia. O texto possui rolagem independente, um botão **Fim** que leva ao último trecho e um rodapé visual que identifica o término. O rodapé não integra o conteúdo copiado ou baixado. Os botões de download do cabeçalho continuam exportando o projeto completo.

## Funções SQL e referências nas regras

O botão **Funções SQL** abre o catálogo de definições importadas ou criadas. É possível buscar, criar um modelo `CREATE OR REPLACE FUNCTION`, editar o SQL completo e excluir uma função. O sistema guarda as definições no JSON do projeto e não executa SQL no banco. Ao renomear uma função pelo editor, o modelador atualiza as referências textuais `#nome` no schema, nas tabelas e nas colunas. Uma função citada em regras não pode ser excluída enquanto suas referências existirem.

Os campos **Regras do schema**, **Regras da tabela** e **Regra** de cada coluna aceitam texto livre. Digitar `#` abre sugestões de funções, filtradas conforme o nome digitado. É possível combinar texto com referências, por exemplo: `O registro é validado por #validar_atualizacao antes da atualização.` Os nomes citados aparecem como atalhos clicáveis para abrir a função correspondente.

Na prévia **Tabela**, TXT e JSON mostram apenas informações próprias da tabela, colunas, chaves, relacionamentos FK, UNIQUEs e CHECKs. O TXT é um resumo legível e não repete comandos de comentário, triggers, índices, políticas nem objetos globais. Na prévia **Esquema** e no download integral, as instruções SQL importadas e as definições globais são preservadas.

```bash
npm test

```

### Testes de interface com Playwright

O Playwright testa o seletor lateral acessível, a navegação entre editor e prévia central, a responsividade, a rolagem independente até o fim, as quebras de linha reais no TXT, a cópia para a área de transferência e o salvamento/cancelamento das regras do schema. A versão do Playwright é fixada no CI e instalada sem alterar o lockfile do projeto.

```bash
npm ci
npm install --no-save --package-lock=false --ignore-scripts @playwright/test@1.56.1
npx --no-install playwright install chromium
npm run test:e2e
```

No GitHub Actions, os testes unitários, a compilação e o Playwright são executados automaticamente na branch `Dev` e nas PRs. O workflow não publica nada no Cloudflare.

A prévia **Tabela** separa linhas com quebras de linha reais, inclusive no texto copiado. O layout usa apenas duas colunas no desktop: menu lateral esquerdo e editor ou prévia central. Não há painel direito, espaço vazio reservado ou sobreposição ao cabeçalho. Em telas menores, o menu lateral aparece acima do editor; o TXT/JSON mantém rolagem interna.

Nomes de tabelas devem ser únicos no projeto; nomes de colunas devem ser únicos dentro de cada tabela. A comparação ignora maiúsculas/minúsculas e espaços nas pontas. Nomes repetidos são rejeitados ao sair do campo ou pressionar Enter, mantendo o nome anterior. Importações com duplicatas são recusadas. Projetos antigos com duplicatas continuam disponíveis para correção, com exportação e cópia bloqueadas até resolver os conflitos.

## Hospedagem no Cloudflare

Endereço: https://nexodblab.pages.dev

A hospedagem usa Cloudflare Pages, servindo apenas o conteúdo de `dist/`. Não há backend nem banco de dados. O favicon da aba do navegador está em `public/favicon.svg`.

Para publicar atualizações com a CLI autenticada na conta do projeto:

```bash
npx wrangler login
npm run deploy
```

Para conferir a configuração sem publicar:

```bash
npm run build
npx wrangler pages dev dist
```

O salvamento continua no `localStorage` do navegador, separado por dispositivo, perfil e endereço do site. Dados salvos em `localhost` não aparecem automaticamente no endereço público: exporte o JSON local e importe no site publicado. Para usar o mesmo projeto em outro dispositivo, transfira o JSON da mesma forma. Limpar os dados do site remove o armazenamento local; mantenha uma exportação dos projetos que quiser guardar.

As explicações de Imutável, UNIQUE, Composto e CHECK ficam em ajudas compactas integradas à borda dos controles, sem ícones soltos nem exemplos: mantenha o mouse parado sobre a opção por três segundos para abrir. Mover o mouse reinicia a espera; sair cancela a abertura ou fecha a mensagem, sem fixação por clique. Os ícones são informativos, sem aparência ou ação de botão. A ajuda de CHECK fica na opção da coluna; o contador apenas expande ou recolhe as restrições. As ajudas também respondem ao foco do teclado e Escape, sem alternar o checkbox. Detalhes de conversão SQL e avisos sobre NULL nas composições usam o mesmo componente.
